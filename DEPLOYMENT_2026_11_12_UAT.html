2 · What changes in the database at start-up

Nothing to run by hand. The new pods add these by themselves when they start:

  • Five new tables: app_roles, app_role_sources, access_grants, feed_template_partition_scans, feed_template_partition_gaps.
  • New columns on existing tables. Every one is new and empty, and none of the existing columns change.
  • Two unique indexes: one on the new release column, and one on the new template-member column of feed_configs. Both columns are new and empty, so the indexes cannot fail on existing data.
  • Three one-time data steps, made so that nobody loses access:
    • Every report permission of level view given before this update becomes runner. From now on view means "open the saved result only", and runner means "may also run the report". Everyone who could run a report before can still run it.
    • Every published report that already has a role list also gets the api_consumer role, so every existing API key keeps reading exactly what it read.
    • The old "who can use this connection" rows are copied into the new access_grants table. Rows that were switched off stay switched off.

3 · Deploy, in this order

  1. Take a database backup. The rollback below needs it only if you want the three one-time data steps undone as well.
  2. Unzip over the source tree of your UAT deployment.
  3. Build these images and push them with the tag you deploy:
    ImageWhy
    querystudio-api (Dockerfile.api)Backend code. The feed worker, scheduler, job worker, downloads and query pods run this image too.
    querystudio-reports (Dockerfile.reports)Same backend code. Build it so that every pod runs the same code.
    querystudio-published-api (Dockerfile.published-api)Same reason.
    UI image (Dockerfile.ui)Frontend code.
    Spark job image (spark/Dockerfile)It changed: it now carries the Databricks JDBC driver. Push it to your registry and put its name in env/uat.site.yaml as sparkK8s.image. The deploy stops with a message naming spark_k8s.image if it is missing.
  4. Helm: deploy EVERY chart, from Charts_2026_11_12_7640e4a34.zip (added 2026-11-12, after this guide was first sent). The update zips carry only what changed, and the query-pods chart was last carried on 11-03, so a UAT deployed without k8s/ since then does not have it. The charts zip is the whole k8s/querystudioapi-helm folder: 9 charts plus env/uat.yaml and deploy.sh. It replaces the k8s/ files in the deployment zip; use it instead of them. Keep your own env/uat.site.yaml, which is not in the zip. Run ./deploy.sh uat, which deploys api, feed-worker, job-worker, scheduler, query-pods, published-api, reports, downloads and ui. Afterwards, oc get deploy -n 45646 | grep query-pods shows querystudio-query-pods-s and querystudio-query-pods-m at 0/0. env/uat.yaml switches these on:
    • Query pods: size s is 4 GB (0 to 2 pods) and size m is 8 GB (0 to 1 pod). Each size starts at 0 pods. A pod is created when a run arrives and removed after 10 quiet minutes. QueryStudio's own scaler does this, because UAT has no KEDA.
    • UAT test mode: every query goes to a query pod, reports included.
    • The run queue, which query pods need.
    • Spark pods in project 45646.
    • Spark Connect is OFF. UAT has no Spark Connect server. Before, env/uat.yaml switched it on and pointed at a server that is not there, so a feed of 500,000 to 10 million rows on "Automatic" was sent to it and failed. Now a feed up to 500,000 rows runs on the QueryStudio worker, and above that on its own Spark pods.
    What the project must allow (Roles, memory) is in section 1 of the pods test guide.
  5. Roll out the new images the way you did for the last update.
AWS portal proxy: the proxy no longer uses the separate proxy username and password on Admin → AWS Portal. It logs in with the same System Account as the portal itself, from Vault. Before you deploy, check that the System Account chosen on that page can log in to the proxy. On the rig, the old fields are read by nothing.

4 · What is new or fixed

WhereNow
Connections with a Vault System Account (the main item)
  • A connection that uses a Vault System Account can be shared, even if an old typed password or old AWS keys were still saved on it. The old values are removed when you share it, and the login comes from Vault only.
  • The AWS portal proxy logs in with the same System Account as the portal.
  • A System Account's "last test" no longer turns red after a page refresh. When a test really fails, it says which step failed.
SnowflakeA query works with no schema chosen. Table names are written the way Snowflake expects them.
Published APIs
  • An API always runs the latest saved version of its query. Before, it could keep running an old copy.
  • Every API's examples now have a Python client (ready to copy). It is one file that reads every row page by page, or in one go with --bulk. It handles retries and "please wait" answers, and signs in with an API key or with AD. A wrong key gives one plain error line.
Who sees a report (app roles)
  • When you publish a report for the first time, you must say who sees it: one or more roles (for example Finance), or everyone. Reports that were published before keep their lists as they are.
  • Admin → Roles and permissions is where roles are managed.
  • A report permission can be given to a role.
  • A person who is refused can press Request access, and the owner is told.
Who can use a connectionIn the connection's dialog, Who can use this connection: everyone, or only chosen roles, AD groups or user groups. It is given to groups, never to one person. A grant to a single person from before is kept and shown as "Person (old grant)".
Feeds
  • Run now → Engine for this run: run any feed once on its own Spark pods, whatever its size. The feed's own setting does not change.
  • Databricks feeds can run on Spark. This is off unless the setting feed_generation.spark_route_databricks is switched on.
  • A month-end template can take its member list from the table's partitions: new codes become feeds at the next start-of-day run.
Reports
  • A date with no data shows an empty report, instead of "schema could not be read".
  • "Explain this" on a number card splits the change by the report's own fields.
ScreensThe side panels (objects panel, query builder sidebar, SQL schema panel, Admin menu) can be resized by dragging their edge. Double-click the edge to reset.
Releases from UAT to PRODThe release pipeline is in the code. In PROD it needs the GitLab settings and a signing key. It does nothing until those are set.

5 · What to test (about 45 minutes)

  1. Vault connection. Take a Portal SSO S3 connection that uses a Vault System Account and still has old keys saved on it. Share it with a group: the share is accepted. Open it: only the Vault account is shown. Someone in that group runs a query on it.
  2. System Accounts. Use Test on an account, then refresh the page: the result stays.
  3. Snowflake. Run a query on a Snowflake connection with no schema chosen.
  4. Publish a new report. You are asked who sees it. Choose a role and check that someone without the role cannot open the report. Open an old report: nothing about its access has changed.
  5. Python client. Published APIs → an API → examples → Python client (ready to copy). Save it, set QS_API_KEY, run python qs_<name>.py --out rows.csv. The row count matches the API.
  6. Spark pods and query pods: follow the pods test guide in this delivery (sections 2 and 3).

7 · Check after deploying (10 minutes)

  • Component Health is green.
  • Connections opens, every saved password shows ***, and an existing connection's Test passes.
  • Open an existing report and run it: the numbers are the same as before, and the same people can open it.
  • Press Run now on a feed: it completes and the file arrives.
  • Run one query: in the project, a query pod starts (the first one takes 1 to 3 minutes) and answers.

8 · If you must roll back

Deploy the 11-10 (or 11-11) images and charts again, or use helm rollback. The older code ignores the new tables and columns. The view to runner step stays in the data, and older code treats runner as at least view. If you want the data exactly as it was before this update, restore the backup from step 1.
