2 · What changes in the database at start-up

Nothing to run by hand. The new pods add these by themselves when they start:

  • One new table: credential_leases. It holds one shared, encrypted copy of each credential QueryStudio obtains: the AWS keys from a portal login, and the password Vault holds for a System Account. A person's own password is never written to it.
  • One new column: business_datasets.sql_param_defaults, new and empty.

No existing column or row changes.

3 · Deploy, in this order

  1. Take a database backup, as usual.
  2. Unzip over the source tree of your UAT deployment.
  3. Build these images and push them with the tag you deploy:
    ImageWhy
    querystudio-api (Dockerfile.api)Backend code. The feed worker, scheduler, job worker, downloads and query pods run this image too.
    querystudio-reports (Dockerfile.reports)The same backend code. Every pod must run the same code: the credential fix shares one copy between pods.
    querystudio-published-api (Dockerfile.published-api)Same reason.
    UI image (Dockerfile.ui)Frontend code.
    The Spark job image did not change.
  4. Helm: keep the charts from Charts_2026_11_12_7640e4a34.zip and run ./deploy.sh uat with the new image tag. Roll every deployment (api, feed-worker, job-worker, scheduler, query-pods, published-api, reports, downloads, ui) so that no pod keeps the old code.

New settings: four new settings, all on by default. You do not need to set them: secrets.lease_enabled (true), secrets.lease_memory_seconds (5), secrets.lease_renew_seconds (30) and secrets.lease_refused_seconds (300).

4 · What is new or fixed

AreaWhat changed
AWS S3 connections stay upBefore: three S3 connections on one AWS account (different buckets) kept dropping, and after a password change in Vault, some pods kept the old password for 20 to 30 minutes. Each pod held its own copy of the AWS keys and the password, renewed on its own clock.
Now:
  • There is one shared, encrypted copy per credential. One pod renews it before it ends, and every pod reads it at use.
  • A password changed in Vault reaches every pod at its next use.
  • When a source refuses a password, it is not asked again for 5 minutes. This stops one wrong password from locking the AD account.
  • When the portal or Vault is down, it is asked a few times in all, not by every reader on every pod.
Snowflake report: business dateA report's business-date parameter now works for any date, not only the date written in the dataset's SQL. The dataset SQL can say {BUSINESS_DATE}. The report's parameter fills it at run time, and the dataset keeps a default value for previews.
Finance grid
  • A saved drill path shows its + / − again.
  • The grid has a place to pick its values. The red "needs at least one value" message goes away once you pick one.
  • A visual changed into a grid no longer keeps hidden fields.
NumbersIDs and codes no longer show thousands separators. The number format is set per field.
Report designerDeleting a visual no longer blocks Save.
Business Query BuilderA query that finds no rows now shows its columns with "0 rows", instead of "Internal server error". It also says plainly when a pick was left out.

5 · What to test (about 30 minutes)

  1. The three S3 connections. Open each one and press Test, then run a report or query on each. Leave them for over an hour, which is longer than the AWS keys last, and run them again: all three still work, with no error.
  2. A password change. Change a System Account's password in Vault, then run a query on a connection that uses it. It works within seconds, on every pod.
  3. A wrong password. Put a wrong password in Vault for a test account and run a query once. You get one clear error, and the AD account is not locked. Put the right password back: the next query works.
  4. Snowflake report. Run it with two different business dates. The rows change with the date.
  5. Finance grid. Open a report with a saved drill path: + / − show. Pick values in the grid. Delete a visual and Save.
  6. Business Query Builder. Run a filter that matches nothing. You see the columns and "0 rows", not an error.

8 · If you must roll back

Deploy the 11-12 images again, or use helm rollback. The older code ignores the new table and the new column, so no database step is needed. If only the credential sharing misbehaves, you can set secrets.lease_enabled to false in the configuration and restart the pods. Each pod then holds its own copy again, as before this update.
