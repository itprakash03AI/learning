Testing Spark pods and query pods on UAT

2026-11-11. For the person testing UAT. Spark pods run feeds; query pods run queries, reports and report-based published APIs. Both are created when work arrives and removed when it is done.

1 · Before you start: what the deployment needs

Deploy EVERY chart. The update zips carry only what changed, and the query-pods chart (k8s/querystudioapi-helm/query-pods) was last carried on 2026-11-03, so a UAT deployed without k8s/ since then does not have it. Use Charts_2026_11_12_*.zip (all charts, the whole k8s/querystudioapi-helm folder) and run ./deploy.sh uat: it deploys api, feed-worker, job-worker, scheduler, query-pods, published-api, reports, downloads and ui. Check after: oc get deploy -n 45646 | grep query-pods shows querystudio-query-pods-s and -m at 0/0.
WhatWhereWhy
The Spark job image, built from spark/ in the release bundle and pushed to your registry env/uat.site.yaml: sparkK8s.image: <registry>/45646/spark-etl:<release> The deploy stops with a message naming spark_k8s.image if it is missing.
Permission for the API and feed-worker pods to create pods in project 45646 The charts create the Role and the spark service account. Your project must allow Roles. Without it a Spark run is refused, with the reason on the run.
Permission for the scheduler pod to scale the query-pod deployments The scheduler chart's rbac-query-pods.yaml QueryStudio's own scaler starts and stops the query pods (UAT has no KEDA).
Memory in the project for the pods Query pods: up to 2 × 4 GB and 1 × 8 GB. Spark: the driver and executors set on Admin → Spark Pods. A pod that cannot be placed stays Pending; the run says so.

The settings themselves are already in env/uat.yaml: query pods on with sizes s (4 GB, 0 to 2 pods) and m (8 GB, 0 to 1 pod), every query sent to a pod (UAT test mode), reports included; Spark pods on, in project 45646, choosing the operator or a plain driver pod by itself.

2 · Spark pods

2.1 Run any feed on Spark, once

  1. Feeds → a feed → Run now.
  2. Engine for this run → Spark cluster. The note under it says: "This run starts its own Spark pods, whatever its size, and removes them when it ends."
  3. Run Feed. The message says the run started "on its own Spark pods".

What you should see

  • In the project, within a minute: a driver pod, then executor pods. 
    oc get pods -n 45646 -l spark-role -w
    When the run ends they finish and are removed.
  • The run completes and the file arrives, with the same rows and values as a run on the QueryStudio worker (run the same feed again with Engine for this run → QueryStudio worker and compare the two files).
  • The feed's own setting has not changed: the next scheduled run uses it as before.

2.2 What Spark is allowed to do here

  • Admin → Spark Pods shows the Spark settings this deployment uses (image, namespace, how pods are created, sizes).
  • GET /api/feeds/backend-options lists the engines and whether each can be used now. If Spark is listed as unavailable, the reason is next to it (for example a missing permission). The Run-now list shows the same.

2.3 Cases to try

CaseExpected
A small feed (a few hundred rows) on SparkCompletes. Spark pods are created even for a small feed when you choose Spark.
A feed left on "Automatic", by sizeUp to 500,000 rows: the QueryStudio worker. Above 500,000 rows: its own Spark pods. (UAT has no Spark Connect server, so it is switched off in env/uat.yaml; before 2026-11-12 it was wrongly on, and a feed of 500,000 to 10 million rows was sent to a server that is not there.) The run's details say which engine and why ("auto_route_large_spark_k8s(rows=...)").
A two-sided feed (cloud + on-prem)Completes on Spark with both sides joined as on the worker.
Stop the run while it is runningThe run says cancelled; the driver and executor pods are removed.
A wrong image name in the site fileThe run fails with "could not pull the image", not a hang.
The source's password changed in VaultThe Spark run logs in with the new one (the login is read for each run).

3 · Query pods (the MotherDuck-style engine)

A query is priced (how much memory it needs) and sent to the smallest size that holds it. The pod runs it on DuckDB, reading S3 directly or the source through its connection, and the answer comes back to the screen as before. Each size starts at 0 pods: a pod is created when a query for it arrives and removed after 10 quiet minutes.
The first query after a quiet spell waits while a pod starts: about 1 to 3 minutes. That is the on-demand behaviour you asked for. To keep a pod ready, set that size's min: 1 in env/uat.yaml.

3.1 See a pod appear

  1. In a terminal: 
    oc get deploy,pods -n 45646 | grep query-pods
    Both deployments, querystudio-query-pods-s and -m, show 0/0.
  2. In QueryStudio, run any query on the SQL page, or open and run a report.
  3. Within about a minute querystudio-query-pods-s becomes 1/1 and a pod starts. The query finishes and shows its rows.
  4. Run more queries: they go to the same pod (2 at a time per pod); with more waiting, a second s pod starts (at most 2).
  5. Leave it for 10 minutes: the pod is removed and the deployment is back to 0/0.

3.2 Where to look in QueryStudio

WhereWhat it says
Admin → Component Health → "query pods (sizes and their scaling)"Healthy, or in words what is wrong with which size (for example "runs waiting 3 min at the maximum").
GET /api/jobs (your own runs)Each run that went to a pod: its size (pod_class), its state and who ran it.
GET /api/jobs/queue/stats (admin)How many runs are waiting, running and done, and whether the queue is on.
The API pod's logFor a run that did NOT go to a pod, the reason: the sizes are not set, the queue is off, the run is priced as small, or (a report) the reports lane is off.

3.3 Cases to try

CaseExpected
The same query on the SQL page twiceThe same rows both times; the second is faster (the pod is warm).
A report run, and the same report as a published APIThe same numbers as before the pods were on (both go to the pods with the reports lane on).
Two people running at the same timeBoth finish; neither waits for the other's run longer than the run itself.
A query too big for 8 GBRefused with "too big for every query pod" in words, never left waiting.
No pod can start (the project is out of memory)After 10 minutes the run fails with the reason; Component Health shows the size as not healthy.
Cancel a long queryIt stops on the pod; the pod takes the next query.

4 · Feeds never run on query pods; reports never run on Spark

A feed runs on the QueryStudio worker or on Spark pods. A query, report or published API runs on a query pod (or in the API pod when the pods are off). That split is by design; the test above uses each where it belongs.

5 · Turning it back

  • Query pods off: remove the industrialization and query_pods blocks from env/uat.yaml and deploy. Every query runs in the API pod again, as before.
  • Spark pods off: sparkK8s.enabled: false. Feeds run on the worker; a feed pinned to Spark is refused with the reason.
  • Production: keep small_run_mb at its default (512): small queries then stay in the API pod and only heavy ones go to a pod.
