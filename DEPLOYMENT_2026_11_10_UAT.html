1 · What is in the zip

177 entries: 175 files (99 backend, 74 frontend, 1 Spark job file and Dockerfile.ui), plus MANIFEST.txt and DELETED.txt. Nothing to delete. No new Python or npm packages. I compared every file in the zip with the commit: all 175 are identical.

Nothing to run by hand in the database. Today's code adds no columns. The two columns from the 11-08 and 11-09 zips add themselves when the new API pod starts, empty: system_accounts.vault_field_map and query_executions.job_id.

One automatic change at start-up: any login header a connection has stored in plain text is encrypted when the new API pod starts. This covers a REST connection's default headers, Trino extra headers and Databricks HTTP headers, under names such as Authorization, X-API-Key, Cookie, or any name containing token, secret, key, auth or password. It is the security fix in section 4. Older code cannot read those encrypted values, so take the backup in step 1 (see section 9).

4 · What is fixed (since the 11-09 zip)

WhereBeforeNow
Snowflake queriesA query returning a NUMBER(p,s) column (a decimal) could fail.Decimals are written as decimals. Whole numbers (NUMBER(p,0)) stay whole numbers, unless a value is too big for one.
Saved login headers (security)A REST / Trino / Databricks login header was stored in plain text, shown unmasked on the Connections page and copied by Clone.Masked, encrypted, and kept with *** like a password (section 1).
Editing a connection (security)An edit could keep the saved password while changing the host, which sent the password to the new host.Refused in words: re-type the password for a new host. Pointing at a different Vault account is allowed and recorded.
REST queries (security)A REST query could send its connection's login to another host.A request that carries a login stays on the connection's own host. A connection with no login may still call other hosts.
Clone of a connection saved long agoClone said "SSL verify changed" and refused, for a source saved before the form had that switch.A missing switch counts as ON, as the connection always behaved. Turning verification OFF while keeping the keys is still refused.
Report parameter bandAn empty parameter that filters at the source read "All".It reads "As in the query", which is what runs.

5 · What to test (about 45 minutes, plus the 11-08 / 11-09 lists)

  1. Screen. On a 1920 monitor at 100%, the screen no longer looks zoomed in and every menu label is on one line. Try user menu → Text size → Larger: the text grows, the menu still fits, and the choice survives a reload.
  2. Snowflake decimals. Run a report or query over a Snowflake table that has a decimal column. It returns the right values, and whole-number columns stay whole.
  3. Clone. Clone an S3 connection to a new bucket, keeping the keys: it reads its tables. Clone it to the same bucket: refused in the popup. Clone a Starburst connection to a new catalog: the password is kept. Change the host while keeping the password: refused in words.
  4. Vault token. On a Databricks connection, or an on-prem Hive connection with a token login, choose a Vault System Account. Test, then run a query.
  5. Published API date. Call a published API with a date parameter set to @PREV_BUSINESS_DAY in CSV and in JSON. Both return the same day's rows.
  6. Designer. Open a report in the designer, add a visual step by step, and accept a suggested field. Then duplicate the tile and delete it.
  7. Headers. If you have a REST connection with an Authorization header, open it: the value shows ***. A query on it still works.
  8. The 11-08 and 11-09 lists, if not done yet.

9 · If you must roll back

Restore the database backup from step 1 together with the previous images (or helm rollback plus the backup). Older code cannot read the login headers this update encrypts, so with the old images and today's database a REST / Trino / Databricks connection that has such a header would fail its login. Without the backup, re-type those header values after rolling back. The two new columns can stay: older code does not read them.
