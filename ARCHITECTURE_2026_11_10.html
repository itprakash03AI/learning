How to read the diagrams

Every diagram uses the same colours, so you can tell at a glance what a box is and what a step does.

Grey — a person or a screen: the browser, a consumer calling an API.
Blue — QueryStudio itself: pods, engines, the code that decides.
Green — stored data: the metadata database, result files, caches. A green arrow = data is read or written.
Purple — a check: who you are, what you may see, whether the answer is correct. A purple arrow = a check happens here.
Amber — outside QueryStudio: source engines, S3, Kafka, Kubernetes, delivery targets.
Blue arrow — an answer or progress reaching the person. Red arrow — a refusal or failure path, said in words, never silent.

1 · The system at a glance

In plain words: One backend image plays several roles; one database is where they all meet. Everything outside — your data, Vault, Kafka, Spark — is reached from there.

Five subsystems share one backend image and one metadata database: connections / catalog, datasets (the semantic layer), reports (builders, canvas, dashboards, exports, published APIs), FeedGen (scheduled file delivery) and DataFlow (a general stage engine). Clockwork is a separate service that fires scheduled jobs; QueryStudio is its authoring plane.

The one idea to hold: pods do not call each other to hand over work. Work is a ROW — a feed run, a queued query, a scheduled job — and the pod that may do it CLAIMS it in the database. The only pod-to-pod HTTP is admin control (run-now / status answered by the daemon's owner) and the Spark job's signed webhook back to the API.

4 · A request, end to end

In plain words: Your click becomes a checked, secured statement, runs once, and is kept as one file that every screen reads from.
  1. Sign-in and gate. The UI calls the API host with a session token (user_sessions); the route declares one capability (require_capability).
  2. Admission. Ad-hoc queries take a slot (core/query_queue.py) and the fleet budget; reports take a typed slot (core/reports/admission.py) — a refusal is 503 with Retry-After, never a silent drop.
  3. Route. Run inline on the API pod, or become a query_jobs row claimed by a sized query pod (core/jobqueue/execute_bridge.py, report_bridge.py).
  4. Engine. SQL is built from the dataset's STORED connections, rewritten by row security, then pushed to the source or run in DuckDB (section 5).
  5. Result. {execution_id}.parquet; the UI reads pages from any pod; progress arrives over the WebSocket.

5 · The brain: what is read, and by which engine

In plain words: Before reading anything, QueryStudio works out the smallest set of files that is sure to hold the answer — and only skips a file when it can prove the file is not needed.

The owner calls pruning the brain of QueryStudio. Its job: read the smallest set of files that is PROVABLY enough, never fewer, and pick the cheapest engine that can read them. Measured on the real fact_tetb: one business date reads 672 of 2,688 files.

Admission and quotas

  • Resource admission (core/resource_admission.py): default auto_throttle — it never refuses; memory clamped to the container; fewer workers rather than starving one below 512 MB.
  • Query-pod reservation (core/query_pods/budget.py): the reservation IS the job row; DuckDB's memory limit = the reservation.
  • Correctness caps refuse: scan budget after pruning, the 50,000-key listing cap, Iceberg files per query. A retry checks refusals first, so it never swallows one.
  • What the user is told: files read out of listed, manifests read, which engine (core/reports/scan_disclosure.py); big runs can go to the background and land in the Download Centre.

Worked example

WHERE business_close_date = DATE '2025-09-30' AND code IN ('51','1000') over Iceberg fact_tetb (identity partitions business_close_date / business_event / code):

  1. The report's result cache is checked; a hit is served only if the snapshot is still current (one LIST).
  2. The snapshot is resolved through the bounded pointer; the filters become Iceberg partition filters.
  3. Both columns are bare, so neither is refused as wrapped.
  4. Warm snapshot: pruned from iceberg_file_stats_v3 with no S3 walk. Cold: manifest-list summaries drop manifests without that date or either code; surviving manifests come from the manifest cache; each file's partition tuple must match (the date by interval overlap, the code exactly — '1000' kept). No bloom: both are partition columns.
  5. The gate: zero files only if proven. The kept list goes to the L1 cache under the filter key.
  6. The read plan types the keys from the current schema and projects by field id; DuckDB reads only those files; one query_pruning_history row records before / after / read.

7 · One query, every source

In plain words: Either the source does the heavy work and sends back only the answer, or QueryStudio reads just the files it needs. Nothing copies a whole table to answer a question.

A user writes ONE statement, or builds it in BQB / CQB, against a connection. QueryStudio never moves a whole table to answer it: either the source's own engine does the work (road A), or QueryStudio's engine reads only the files the brain proved are needed (road B). When the statement needs two sources, each side takes its own road and only the two results meet (road C, section 8).

What is decided before a byte is read

  1. Which connection. A report reads the dataset's STORED connection_ids; a missing one raises — it never falls back to local DuckDB (the three-week incident).
  2. May this person build on it. Connection access by role / group is checked in the builders only (BQB, CQB, the SQL page, browse, datasets). Running a report, a dashboard, a feed or an API never re-checks the connection — the report's own access is the gate.
  3. Which rows. Row security rewrites the statement in the SOURCE's dialect (a Trino side is secured in Trino grammar, an S3 side in DuckDB grammar).
  4. Which dialect. The SQL's dialect is DECLARED on the connection (config.sql_dialect) and translated by core/sql_dialect_translator.py when DuckDB runs it; the run records from and how (declared / configured / guessed). || is string concatenation, never OR.
  5. Which files (road B only): the brain, section 5.
  6. Which engine and where: inline, a DuckDB child process (a crash never kills the API), a sized query pod, or Spark for feeds (section 5, engine routing).

The answer is always one parquet file named by the execution id. The UI reads it page by page from ANY pod, the canvas draws tiles from it, exports stream from it, and a published API serves its pages from it — nobody runs the query a second time to show it.

8 · Two sources in one answer: cloud 2M ⋈ on-prem 1M

In plain words: Both sides are fetched at the same time and written to disk, then joined on disk. If either side fails you get an error — never half an answer that looks complete.

Example: the cloud side is fact_tetb on AWS S3 (2,000,000 rows after the business-date filter), the on-prem side is fact_tetb_ext on Starburst / Hive (1,000,000 rows); they are joined on the trade key. Every surface — the query builder, the SQL page, a raw-SQL report, a merged dataset, a federation view, a published API, a feed, a DataFlow stage — goes through ONE capability: core/executors/cross_source_combine.py. Before it there were four engines with four answers (one silently dropped the on-prem side).

What happens, in order

  1. Checked before anything runs. combine_spec normalises the join type (inner / left / right / full / cross; outer = full) and refuses a keyless join, unequal key lists or an unknown mode with a 400. An unsupported side type is refused, naming what is supported.
  2. Each side secured by the caller, in its own dialect, before it reaches the core.
  3. Both sides start together on two threads (execute_cross_source). The cloud side runs on road B (DuckDB reads only the pruned files); the on-prem side runs on road A (Starburst computes, rows stream back 10,000 at a time). Neither side is ever held in memory: each lands on disk as primary_<tag>.parquet / secondary_<tag>.parquet in a private work directory.
  4. One side fails → the whole run fails. A shared cancel event stops the other side; the partial output is deleted. QueryStudio never returns the cloud rows alone as if they were the answer.
  5. The join runs in DuckDB, not in Python. combine_sides reads both parquet files under the per-query memory limit (query_engine.duckdb_memory_limit_mb, default 2,048 MB; a query pod uses its reservation) and SPILLS to the temp directory when the join is bigger than memory. Measured: a 2.4M × 2.4M inner join under a 256 MB limit peaked at 283 MB; the old pandas merge needed 793 MB and could not spill.
  6. Mismatched key types are handled in the open. If one side's key is text and the other's a number, both are compared as text and the cast is DISCLOSED (key_casts); DuckDB would otherwise refuse VARCHAR = BIGINT.
  7. The row limit bounds the RESULT, not each side. DuckDB is asked for limit + 1 rows; only if that extra row exists is the result marked truncated, so exactly-the-limit is reported complete.
  8. The record says what happened (CombineOutcome.disclosure()): primary rows 2,000,000, secondary rows 1,000,000, result rows, truncation per side and for the result, key casts, join health, and whether the pushdown below was used.

Semi-join pushdown: when the on-prem side is small

For an INNER or RIGHT join whose primary is a SQL source, the core runs the SECONDARY first. If its join keys have at most 10,000 distinct values (integers or plain strings, up to 8 key columns), the primary statement is wrapped with WHERE key IN (…) in the primary engine's own grammar, so the big side only returns matching rows. If that engine rejects the wrapped statement, it runs unfiltered — the pushdown is an optimisation, never needed for correctness. LEFT and FULL joins never push down: they exist to keep unmatched rows. Recorded as semi_join_pushdown: applied / skipped / declined.

The same two sides in a FEED

  • One SQL text for both sides. query_params.table_map renames tables per side (icbg.fins → hive.fins), parsed with sqlglot so a literal or a comment is never touched.
  • Union by column NAME, decided once for every lane (merge_by_name.plan_merge): names matched ignoring case (Trino folds to lower, Oracle to upper), output in the cloud side's order, a missing column filled with a typed NULL, no de-duplication. Incompatible types refuse and name the column.
  • Zero-copy union. For a union, the two side files are not rewritten: a parts manifest stacks them (build_union_parts_manifest). The DuckDB rewrite it replaced ran out of memory on 1M rows × 460 columns.
  • Certification per side. ROW_COUNT per side; the run is certified only when combined rows = cloud + on-prem.
  • Large runs go to Spark (section 5 routing): the Spark job reads both sides and merges with the byte-identical mirror spark/jobs/qs_merge_by_name.py (spark_union_by_name / spark_join), and ships the same record back.
  • Optional staging (backend_config.stage_to_s3): a side is uploaded to S3, downloaded fresh and checked (size, sha256, footer rows) before the merge reads it.

9 · Published APIs, call by call

In plain words: An outside system asks with a key; most calls are answered from a file already made. When a new answer is needed, one request makes it and everyone else waits for that one.

A published API (a "published view") is a report, a saved query or a federation view exposed at /api/v1/views/{slug} for systems outside QueryStudio. It runs on the published-api pod (the management routes answer 404 there). The data is never copied into an API table: every call is served from the same stored-result model as the UI.

The call, in order (api/published_views_api.py::ext_get_view_data)

  1. Who is calling. An API key (stored as sha256) or a signed-in AD user; capability published_api.consume. A key is scoped to the views it may call; a view may also be limited to AD groups.
  2. Rate limit per key: 60 calls a minute by default, up to 300.
  3. Parameters and filters. Date tokens (@TODAY, @PREV_BUSINESS_DAY:LDN, -1d, ${monthEnd}) are resolved AT THE DOOR to the ISO day they name, so the cache key names the day. A multi-select parameter takes several values. Consumer filters must be on the view's allowed list and are merged with the publisher's fixed filters.
  4. Cache lookup. The key is the view + the resolved question. A HIT reads the page from the stored parquet — the source is not touched.
  5. MISS: one leader. Identical requests in the same process wait on one in-flight run; across processes a "cold flight" lets one request materialise while the others wait and then read its file.
  6. Capacity, said plainly. A worker near its memory share answers 503 with Retry-After instead of being killed; the pod's lane slot is waited for up to 30 s, then 429.
  7. The source handler — one per source type, a registry not an if-chain: saved_query, business_report, federation (cross-source views go through section 8's core). The consumer's identity goes with it, so row security filters as THAT consumer, and the result is stamped with what it was filtered by.
  8. Only what the page needs. A page materialises offset + limit + 1 rows (grown ×2 when a pager goes further), plus a manifest with the truth: total rows, exact or at-least.
  9. The answer. Rows + pagination (total_rows, has_more, next_page_url, dataset_version) and the header X-QS-Dataset-Version.

10 · Feeds: scheduled file delivery

In plain words: Every morning each feed gets one run for its business date; it waits for its data, builds the file, checks it, delivers it, and is marked delivered only if every hop arrived.
  • The business date is derived from the feed's schedule rule and its business calendar (schedule.business_date_for: run day, current or previous month end), never from activity.
  • Exactly one run per feed and date: partial unique indexes on feed_runs; a missed date is caught up or recorded in feed_sod_gaps.
  • Dependencies: four verdicts (met / not met / not expected / could not tell); two roads to one resolver — the Kafka topic and the QS_KAFKA_MESSAGE table — de-duplicated by message identity; the poller walks every held run in pages.
  • Engine stages, in code order: status_running → query_{backend} → format_{fmt} → integrity_local → row_count_check → deliver_{dest} → integrity_post_delivery. The row-count check runs BEFORE delivery, so a bad count never leaves the building.
  • Delivery: per-hop rows in delivery_attempts; chain_verdict = DELIVERED only if every hop succeeded (no outcomes = FAILED). A failed hop can be retried over the SAME certified file without regenerating; re-sending a hop that already succeeded is backlog B7.
  • Steps: feed_run_steps, one row per step per attempt; a step re-runs only if it DECLARED itself re-runnable (undeclared = refused — the lesson of 50M duplicate rows).
  • Restatement (WD2..WD6 re-sends) is a POLICY row (feed_restatement_policies), not code.

12 · The security plane

In plain words: Five questions in a fixed order: who are you, may you use this screen, may you use this thing, which rows may you see, and are the secrets safe at rest.
  • Tool entitlement (core/tool_entitlement): what a person may DO — 63 capabilities; ONE decision can(), cached and invalidated across pods; an unreadable store answers 503, never a silent no.
  • Access to things (core/entitlements.py): reports by application role; connections (phase 1, on its branch) by role / AD group / user group, checked only while someone BUILDS — never on a report, dashboard, feed, file or run.
  • Row security (core/row_security): permissive policies OR'd, restrictive AND'd. A signed-in person holding no grant on a table that has grants gets no rows; a table with only restrictive policies (or none) is served unrestricted, and the audit says so; an unresolved principal (share link, a background run) on a governed table is refused.
  • Secrets: envelope encryption — the master key only unwraps the data keys in encryption_data_keys; only the API pod bootstraps them. System Account secrets come from Vault and are refreshed on every pod after a rotation (core/qs_credentials/freshness.py). A Spark run's credentials live in a per-run Secret deleted when the run ends.

13 · Traps and known risks

Open risk — a truncating cap. limits.max_registered_files (5,000) keeps the LAST 5,000 Iceberg files after pruning and still answers 200 (core/duckdb_views.py::_apply_registered_files_cap). It is shown to the user and the completeness certificate says INCOMPLETE, but it contradicts the rule that a correctness gate must fail. Changing it to a refusal changes behaviour for very large reads — tracked for a decision.
Open risk — row security needs the principal. execute_dataset_query with no user context only WARNS and skips row security. Every caller today passes one; any NEW caller must, and token callers must pass the unresolved marker.
